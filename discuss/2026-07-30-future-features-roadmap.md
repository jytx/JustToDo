## 3. AI 智能助手

JustToDo 最具差异化的方向。按能力分三层，可逐层落地。

### L1 — 自然语言建任务（最易落地，性价比最高）

- **价值**：在 `AddTaskBar` 输入「明天下午3点和老板开会 #工作，优先级高」，
  自动解析出：截止时间、标签、优先级、标题。
- **设计要点**：
  - 复用已有 `AddTaskBar` 的标签选择能力，再接一层 NLP 解析。
  - **第一版用规则 + 正则起步**（"明天/后天/下周一/下周三下午3点" 这类常见表达），
    完全本地、零依赖、零成本。
  - 解析结果在输入框下方做**实时预览**（"将创建：标题=xxx，截止=xxx，标签=xxx"），
    用户回车前可纠错。
- **数据模型**：无改动。
- **复杂度**：⭐⭐（纯前端解析，可逐步增强词表）

### L2 — 任务拆解 / 笔记总结（需接 LLM）

- **价值**：
  - 选中一个大任务 → 「AI 拆解子任务」→ 生成 3–5 个子任务草稿，用户确认后入库。
  - 选中一篇笔记 → 「生成摘要 / 提取待办」→ 把笔记里的行动项抽成任务。
- **设计要点**：
  - **要做 provider 抽象层**（类似 `holiday.rs` 的降级思路）：
    - 云端：OpenAI / 智谱 GLM 等，用户在设置页填 key。
    - 本地：Ollama（隐私好，但用户要自己装模型，体验门槛高）。
  - AI 功能**默认关闭**，用户在设置里显式开启并配 key，避免强加给所有人。
  - 拆解/总结结果一律**先给草稿，用户确认**再写库，不自动落库。
- **关键决策**：第一版是否支持本地 LLM（Ollama）？
  - 建议**第一版只做云端 API**，降低复杂度；本地模型作为后续 provider 扩展。
- **数据模型**：无改动（结果直接复用 task/note 结构）。
- **复杂度**：⭐⭐⭐（provider 抽象 + 流式 UI + 设置页配置）

### L3 — 语义搜索（高级，远期）

- **价值**：当前搜索是纯文本匹配。语义搜索能命中「上周关于招聘的事」这类模糊意图。
- **设计要点**：需要 embedding，对笔记/任务做向量化存储与检索。
- **复杂度**：⭐⭐⭐⭐（成本高，建议 L1/L2 验证后再投入）

## 4. 系统通知 + 重复任务

任务 App 的「基本盘」，目前缺失，做完会让功能完整度明显提升。

### 系统通知

- **价值**：到点提醒，驱动日活。
- **设计要点**：
  - 用 `tauri-plugin-notification`。
  - Rust 端起一个**调度器**（后台线程，定时扫描到期 `remind_at`）。
  - **关键决策：应用关闭后还要提醒吗？**
    - 建议第一版只做**应用运行时提醒**，简单可靠。
    - 若要离线提醒，需注册系统级调度（macOS launchd / Windows 任务计划），
      复杂度显著上升，列为后续增强。
- **数据模型**：
  - tasks 加 `remind_at`（单时间戳）起步。
  - 若要多提醒（"提前 15 分钟 + 到点"），新建 `task_reminders` 关联表。
- **复杂度**：⭐⭐⭐

### 重复任务（rrule）

- **价值**：覆盖「每周一三五健身」「每月报销」等日常打卡场景。
- **设计要点**：
  - tasks 加 `rrule` 字段，存 RFC 5545 规则字符串（如 `FREQ=WEEKLY;BYDAY=MO,WE,FR`）。
  - 完成一个重复任务时，**按 rrule 计算下一次 due_at，自动生成新实例**。
  - Rust 端用成熟的 `rrule` crate 计算。
- **与「清单生成计划」的关系**：
  - 清单计划 = 「按规则批量生成一组清单项」；
  - 重复任务 = 「单个任务自我复制下一个实例」。
  - 概念上有重叠，**建议保持两套独立机制**，避免互相耦合变复杂。
- **复杂度**：⭐⭐⭐

## 5. 数据导入 / 导出

降低用户迁移成本、赢得「数据不锁死」的信任，对本地应用尤为重要。

### 导出

- **Markdown**：每个任务/笔记一个 `.md`（标题=文件名，正文=备注/富文本，
  frontmatter 放元数据：清单、标签、优先级、截止、创建时间）。笔记天然适合。
- **JSON 全量备份**：结构化导出所有表，用于自备份或迁移到自建后端。
- **iCal**：把有截止时间的任务导出为日历文件，可订阅到系统日历。
  与已有日历视图互补（一个看，一个往外发）。

### 导入

- **TickTick / Todoist**：二者都支持 CSV 导出，做字段映射即可。
  这是**拉新用户最直接**的方式。
- **Markdown 导入**：与导出对称。

### 架构

- Rust 端做文件读写（已有 `save_image` 的文件操作基础）；
  前端做格式转换与字段映射。
- 入口：设置页加「数据管理」区块。

- **复杂度**：⭐⭐（纯 IO + 字段映射，无架构难点）

## 6. 看板视图（Kanban）

列表视图的补充，适合「按状态/优先级流转」的场景。

### 核心问题：列（column）怎么定义？

- **方案 A（推荐第一版）—— 基于现有字段派生**：
  用「标签 / 优先级」作为列。
  - 几乎不改数据模型，主要是新增一个 `BoardView.vue`。
  - 拖动卡片 = 修改任务的标签/优先级，复用现有 `updateTask`。
- **方案 B —— 引入自定义列**：
  新增 `board`（看板 = 一组列定义）概念，任务挂到某列，类似 Trello。
  灵活但改动大。

### 设计要点

- 用拖拽库（vuedraggable / Arco 拖拽）实现卡片跨列拖动。
- 与列表视图、日历视图并列，作为第三种视图模式。
- 列定义可配置（按哪个字段切分、显示哪些列）。

- **复杂度**：⭐⭐⭐（主要是拖拽交互和 view 层）

## 7. 批量操作

体验刚需，做起来不复杂，但容易被忽略。

### 触发方式

- 列表项左侧出现复选框（进入「多选模式」），底部浮出操作栏。
- 支持全选、Shift 多选。

### 支持的批量操作

- 改清单 / 改标签（多选追加）
- 改优先级 / 改截止日期
- 归档 / 删除
- 标记完成

### 实现要点

- `task.ts` store 加 `selectedIds: Set<string>` 状态，列表组件监听它渲染选中态。
- 批量操作本质是循环 `updateTask`，但要**包成一个批量 IPC 命令**
  （如 `bulk_update_tasks`），避免 N 次往返、且保证一次事务。
- 需同步更新 `currentTasks` / `subtasks` / `subtaskCache` / `selectedTaskObj`，
  遵循现有 `updateTaskInArray()` 的响应式套路。

- **复杂度**：⭐⭐（前端多选状态 + 一个批量后端命令）

## 8. 子任务进度条

小而美，提升信息密度，半天工作量。

### 设计

- 父任务行内显示 `▰▰▰▱▱ 3/5` 或圆环进度，hover 显示百分比。
- 进度 = **已完成直接子任务数 / 直接子任务总数**（只算一层，简单直观，
  避免多层嵌套时的语义模糊）。

### 可选增强（有争议，建议做成设置项）

- 完成全部子任务时，自动询问「是否标记父任务完成」。

### 实现

- **数据模型：无需改动**。
- 运行时按 `parent_id` 聚合计算。
- 若层级深、列表项多，可在 `subtaskCache` 里缓存进度值，避免重复全量扫描。

- **复杂度**：⭐

## 9. 多窗口

已有「任务详情面板」的延伸：把某个任务/笔记**弹出成独立窗口**，
适合对照写作或长时间编辑。

### 两种实现层级

- **方案 A —— 同一 webview 内的"浮窗"**：
  Vue 渲染一个可拖拽浮动面板，本质仍是主窗口一部分。
  简单，但会被主窗口遮挡，不是真窗口。
- **方案 B —— 真正的 Tauri 多窗口**（推荐）：
  用 `WebviewWindow` API 创建新窗口，每个窗口加载同一前端但不同路由
  （如 `/#/task/123`）。窗口间用 Tauri event 通信。

### 难点：多窗口状态不共享

- Tauri 每个窗口是**独立 webview，Pinia store 不共享**。
- 需要 event bus 同步，或每个窗口从 DB 重新加载。这是主要工作量。

### 建议

- 做方案 B，但**克制使用场景**：只允许「笔记编辑」弹出独立窗口
  （笔记适合长开），任务详情仍用内嵌面板。
- **复杂度**：⭐⭐⭐⭐（窗口间状态同步是真正的难点）

## 10. 桌面小组件 / 常驻浮窗

在桌面常驻一个「今日待办」小窗。

### 实现思路（Tauri 2）

- 创建一个**无边框、置顶、半透明**的独立窗口，只渲染今日任务列表。
- 可拖动、可吸附屏幕边缘、可折叠成一个小条。
- 配合「开机自启 + 启动后最小化到桌面角落」。

### 进阶（不建议第一版）

- 做 macOS 原生 WidgetKit 小组件需要写 Swift 扩展，复杂度极高。
- 用 Tauri 浮窗方案足够，且跨平台。

- **复杂度**：⭐⭐⭐（主要是窗口样式调教 + 置顶/吸附交互）

## 优先级总览

按「价值 ÷ 复杂度」排序的推进建议：

| 优先级 | 功能 | 理由 |
|--------|------|------|
| 🥇 P0 | **子任务进度条** | 半天搞定，立竿见影提升质感 |
| 🥇 P0 | **批量操作** | 体验刚需，复杂度低 |
| 🥈 P1 | **数据导入/导出** | 建立用户信任，拉新利器 |
| 🥈 P1 | **AI 助手 L1（自然语言建任务）** | 差异化，可先不依赖外部 API |
| 🥉 P2 | **系统通知 + 重复任务** | 基本盘，但涉及后台调度，工作量不小 |
| 🥉 P2 | **看板视图** | 价值看个人，A 方案可快速试水 |
| 🥉 P3 | **桌面浮窗** | 锦上添花 |
| 🥉 P3 | **多窗口** | 真正多窗口的复杂度不值当前阶段投入 |
| 🥉 P3 | **AI L2/L3** | 等 L1 验证后再投入 |
